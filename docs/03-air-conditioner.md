# 空调（device=3）JSON、Lua 与红外格式

[返回通用说明](../README.md)

数据来自 [ysard/mi_remote_database](https://github.com/ysard/mi_remote_database)。

空调是当前码库中唯一同时包含固定按键码和动态状态协议的设备。电视、风扇、灯泡等设备可以把一个按键直接解密成一组红外时长；状态型空调则要把电源、模式、温度、风速和扩展功能合成完整状态，再生成一帧或多帧红外波形。

## 数据位置与数量

```text
3_AC.json
3_AC/<brand>_<brandId>.json
3_AC/models/<modelId>.json
```

- 品牌：280；
- 型号：1828；
- 型号全部由品牌文件的 `others` 引用；
- `type=1` 固定码型号：68；
- `type=2` 状态型型号：1760；
- 字符串 key：33779；
- 数组 key：1718；
- 载波范围：33000～38800 Hz；
- 最常见载波：38000 Hz，共 1502 个型号。

这批空调型号的来源均标记为 `kk`。纯数字型号 ID 和 `kk_` 前缀并不能决定编码方式，实际分支必须读取 `type` 和 `key` 的值类型。

## 代表性数据示例

这里选择格力 `72_2807`。它是 `type=2` 状态型空调，同时具有基础模板、模式能力、逻辑波形、扩展功能和两种 Lua 脚本，能够代表空调数据与其他设备的主要差异：

```text
3_AC.json
  → 3_AC/Gree_72.json
    → others[]._id 中的 72_2807
      → 3_AC/models/72_2807.json
```

### “开机”功能的完整处理过程

下面是 `72_2807.json` 中这次开机编码实际涉及的原始字段。这里只从原对象中删去未参与本次操作的字段，保留值没有改写：

```json
{

    "key": {
      "1001": "00020520",
      "1002": "0E23CB26010024030F380000000083",
      "300": "3660,1800",
      "301": "400,400",
      "302": "400,1400",
      "306": "1",

```

字段 `1522` 的完整原值在 JSON 中是字符串；按换行还原后如下：


实际执行步骤如下：

1. `RemoteCatalog.loadRemote()` 读取 `type=2`、`frequency=38000` 和整个 `key`，调用 `AcConfiguration.parse("72_2807", key)`。`1002`、`300～302`、`306` 和 `1522` 保存到 `rawFields`；`1515` 与 `888888` 生成定时和睡眠扩展功能。
2. `createInitialState()` 得到关机初始状态：`power=1, mode=0, temperature=26, fanSpeed=0, windDirection=0`。此配置的定时范围从 10 开始，所以初始扩展状态是 `{9=10, 10=10, 22=0}`。
3. 用户点击开机时，界面执行 `state.withPower(0)`，并以 `functionId=1` 调用 `normalizeState()`。电源操作会把定时开、定时关和睡眠全部复位，结果为 `{9=0, 10=0, 22=0}`。
4. `KkAcLuaEncoder.encode(configuration, state, 1)` 调用 `fieldsForFunction(1)`。本型号的 `888888` 没有 `fid=1` 覆盖，因此继续使用基础字段。
5. `template(1002)` 把十六进制 `0E23CB26010024030F380000000083` 转为字节。开头 `0E` 等于后续字节数，因此它是长度头并被移除，基础状态字节为：

   ```text
   23 CB 26 01 00 24 03 0F 38 00 00 00 00 83
   ```

6. 这个型号没有 `1017`，`applyFunctionRules()` 不修改字节。`runLua()` 执行上面的 `1522`：当前 `power=0`，但 `exts[10]=0`，所以不生成关机定时；最后重新计算第 14 字节校验和。Lua 后的字节仍为：

   ```text
   23 CB 26 01 00 24 03 0F 38 00 00 00 00 83
   ```

7. `buildWave()` 使用 `300=[3660,1800]` 作为引导码，`301=[400,400]` 表示逻辑 0，`302=[400,1400]` 表示逻辑 1。`306=1` 表示每个字节低位优先。组装结果为 228 个微秒时长，总时长 122460 µs。

## `type=1`：固定按键码

`type=1` 的结构与电视等普通遥控器相同：

```json
{
  "data": {
    "type": 1,
    "frequency": 38000,
    "key": {
      "power": "Base64...",
      "power_r": "Base64..."
    }
  }
}
```

处理流程为：

```text
Base64 → AES-256-ECB → GZIP → JSON int[] → ConsumerIrManager
```

固定码 AES 使用 `AES/ECB/NoPadding`，不需要 IV。公共密钥是：

```text
fd7e915003168929c1a9b0ec32a60788
```

密钥是 32 个 ASCII 字节。AES 解密后先删除明文尾部的 `0x20` 填充空格，再进行 GZIP 解压。

当前 68 套 `type=1` 配置共解析出 685 个正向按键。`<key>_r` 是反向码，不应该在界面中显示成另一个功能。

## `type=2`：完整状态编码

`type=2` 的 `key` 不再是“按键名到固定红外码”的简单映射，而是一组协议规则。例如：

```json
{
  "1002": "0E23CB26010024030F380000000083",
  "1504": "T|S&0",
  "1505": "T|S&0,2,3",
  "300": "3660,1800",
  "301": "400,400",
  "302": "400,1400",
  "1518": "Lua 脚本",
  "1522": "bit32 版本 Lua 脚本",
  "888888": []
}
```

空调每次操作都从完整状态生成红外数据。当前状态至少包括：

- 电源；
- 模式；
- 温度；
- 风速；
- 上下和左右风向；
- 灯光、睡眠、强力、定时等扩展功能。

代码中只保存协议公共编号：

```text
电源：0 = 开，1 = 关

模式：
0 = 制冷
1 = 制热
2 = 自动
3 = 送风
4 = 除湿

风速：
0 = 自动
1 = 低风
2 = 中风
3 = 高风
```

某个型号支持哪些模式、温度、风速和扩展功能，必须从该型号 JSON 解析，不能在代码中按品牌写死。

## 小米原版 KK 空调链路

从 `KKACManagerV2`、`NormalCodeHelper`、`CodeHelper` 和 `ACStateV2` 的调用关系可以确认，原版并不是只运行 Lua：

```text
ACStateV2 完整状态
  → NormalCodeHelper.getWaveCodes(...)
  → CodeHelper.encProxy(...)
      → libkksdk.so 的 enc 或 enc2
      → 基础状态字节帧
  → 执行 1518 Lua
  → 按功能选择 FormatParam
  → Java getWaveCode(...)
  → 最终红外波形
```

`NormalCodeHelper` 会把编号大于 1000、小于 1501 的规则传给：

```java
CodeHelper.initRemote(remoteId, 1, rules);
```

这说明 Lua 接收到的 `bytes` 在原版中已经经过 `enc` 或 `enc2`。Lua 主要继续处理特殊功能位、校验、定时、多帧重组和扩展状态，并不能据此认定 Lua 完整替代了 native 编码器。

### `libkksdk.so` 的边界

Java 层可以确认这些 JNI 方法：

- `init(Context, String)`；
- `initRemote(int remoteId, int type, String[] rules)`；
- `enc(...)`；
- `enc2(...)`；
- `release(int remoteId)`。

`libkksdk.so` 不是只处理几个特殊 key。基础状态编码也会进入 native 层，`ZipCodeHelper` 同样会加载它。当前项目中的 `KkAcNativeBridge` 只是预留接口：初始化失败、编码返回空值、释放不执行操作。

## 当前 JSON 与 LuaJ 链路

当前项目没有真实调用 `enc/enc2`，使用的是一条可独立运行的替代路径：

```text
读取型号规则
  → 合并当前功能的 888888.exts
  → 检查 1510 自定义波形
  → 从 1002 创建基础模板
  → 应用目前已解释的 1017 扩展状态位
  → 执行 1522 或兼容的 1518
  → 使用 309/310 或 300～307 组装波形
  → 应用 1508/1509
  → 校验波形结构
```

1760 套 `type=2` 配置都能创建状态对象，并能为初始电源操作生成非空、正时长、偶数长度波形。这个结果证明数据可以被解析和组装，不等于所有状态都与小米原版输出一致。

不使用 `libkksdk.so`、只用 JSON 和 LuaJ 的路径已经实际控制过格力空调。这证明部分格力协议可以工作，但不能外推到全部品牌、全部型号和全部功能。

## Lua 与 LuaJ

项目使用：

```kotlin
implementation("org.luaj:luaj-jme:3.0.1")
```

`3.0.1` 是 LuaJ 库版本，不是 Lua 语言版本。LuaJ 3.0.x 更接近 Lua 5.2，支持 `bit32` 风格：

```lua
bytes[1] = bit32.bor(bytes[1], 0x40)
```

它不能直接解析 Lua 5.3 位运算符：

```lua
bytes[1] = bytes[1] | 0x40
```

受影响的运算符包括 `&`、`|`、`~`、`<<` 和 `>>`。JSON 中常见两份脚本：

- `1518`：旧脚本，部分配置直接使用 Lua 5.3 位运算符；
- `1522`：通常把位运算改写为 `bit32.band`、`bit32.bor`、`bit32.lshift` 和 `bit32.rshift`。

当前逻辑优先运行 `1522`，没有时再检查 `1518`。如果唯一的 `1518` 包含 LuaJ 不支持的语法，就不能直接执行。

传入脚本的全局变量包括：

```text
bytes, power, mode, temperature, windSpeed,
udWindMode, functionId, exts
```

`bytes` 使用 Lua 的 1 起始索引。脚本既可以修改表中的元素，也可以创建新表并替换全局 `bytes`。

## `1000～1017` 状态规则

| 字段 | 当前理解 |
|---|---|
| `1000` | 算法标识，完整取值未知。 |
| `1001` | 电源规则。 |
| `1002` | 基础状态字节模板。 |
| `1003` | 温度规则。 |
| `1004` | 模式规则。 |
| `1005` | 风速规则。 |
| `1006` | 左右风向规则。 |
| `1007` | 上下风向规则。 |
| `1008` | 校验规则，算法尚未完整确认。 |
| `1009` | 独立功能规则。 |
| `1017` | 扩展状态到位范围的写入规则。 |

`1001～1009` 不是 Lua，也不是最终波形。原版会把这些紧凑规则交给 `initRemote` 和 `enc/enc2`。

样本还包含 `1010`、`1011`、`1012`、`1013`、`1015` 和 `1016`。目前没有足够证据给这些字段确定统一含义，解析器应该保留原始值，不能按猜测丢弃。

## `1501～1507` 模式能力

| 字段 | 当前理解 |
|---|---|
| `1501` | 制冷能力。 |
| `1502` | 制热能力。 |
| `1503` | 自动能力。 |
| `1504` | 送风能力。 |
| `1505` | 除湿能力。 |
| `1506` | 上下风向可选值。 |
| `1507` | 样本中存在，完整含义尚未确认。 |

模式字段是由多个片段组成的能力表达式：

- `NA`：不支持这个模式；
- `T`：当前按温度不可调处理；
- `T&16,17`：温度存在排除或限制列表；
- `S`：当前按风速不可调处理；
- `S&0,2,3`：排除自动、中风和高风，只保留低风；
- `T|S&0,2,3`：同时组合温度与风速约束。

没有 `T` 时，当前解析器使用默认温度范围 16～30 ℃；没有 `S` 时使用默认风速范围 0～3。这里的默认值是码库约定，不代表所有真实空调都具备这些档位。

## 波形字段

| 字段 | 当前理解 |
|---|---|
| `300` | 引导码。 |
| `301` | 逻辑 0 波形。 |
| `302` | 逻辑 1 波形。 |
| `303` | 字节后延时，索引 `-1` 表示帧尾。 |
| `304` | 帧长度。 |
| `305` | 协议或码制编号，编号表未知。 |
| `306` | `1` 表示低位优先。 |
| `307` | `1` 表示移除默认尾部逻辑 1 的首个 mark。 |
| `309` | 多符号波形组。 |
| `310` | `309` 路径的符号或字节限制。 |
| `1508` | 重复次数。 |
| `1509` | 指定字节使用的 bit 数。 |
| `1510` | 按功能和状态提供完整自定义波形。 |
| `1514` | `ZipCodeHelper` 使用的压缩或二进制自定义波形。 |

当前 Java 波形组装器支持 `300～303`、`306/307`、`309/310`、`1508/1509` 和 `1510`。

## 扩展功能字段

| 字段 | 当前理解 |
|---|---|
| `1515` | 扩展功能 ID、状态范围、电源条件和支持模式。 |
| `1516` | 根据按键或状态选择功能专用格式。 |
| `1517` | 功能互斥或状态复位规则。 |
| `1518` | Lua 脚本。 |
| `1522` | 常见为使用 `bit32` 的兼容 Lua 脚本。 |
| `600` | 条件过滤和目标状态赋值。 |
| `888888` | 扩展功能定义和当前功能的字段覆盖。 |
| `99999` | `ZipCodeHelper` 二进制格式参数。 |

`888888` 是数组，常见元素为：

```json
{
  "fid": 22,
  "fname": "",
  "fkey": "sleep",
  "exts": {
    "1002": "...",
    "300": "..."
  }
}
```

- `fid`：功能编号；
- `fname`：功能名称；
- `fkey`：备用名称；
- `exts`：发送该功能时覆盖基础配置的字段。

`888888.exts` 不能忽略。定时或睡眠功能可能替换 `1002`、`300～303`、`305/306`、`1508/1509`，形成不同于普通状态操作的帧。

## 格力 43 套配置

格力品牌文件为：

```text
3_AC/Gree_72.json
```

43 套配置中包含 3 套 `type=1` 和 40 套 `type=2`。许多配置看起来相近，但状态模板、模式位、风速位、校验、帧长度、帧间延时、风向、定时、扩展功能、Lua 或 `305` 都可能不同，因此不能按字段相似度合并。

目前已经确认：

- 43 套配置都能通过品牌索引找到并解析；
- 3 套固定码配置走公共 AES/GZIP 路径；
- 40 套状态型配置走状态模型、JSON、LuaJ 和 Java 波形组装；
- 不使用 `libkksdk.so` 的路径已经实际控制过格力空调。

目前不能确认：

- 43 套配置的每个功能都能控制真实设备；
- 所有状态组合都与小米原版输出一致；
